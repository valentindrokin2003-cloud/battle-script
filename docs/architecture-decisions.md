# Архитектурные решения (ADR)

Только дорогие или трудно обратимые решения — не полная история (она в [`docs/superpowers/specs/`](./superpowers/specs/)) и не текущий снимок (он в [`docs/architecture/hld.md`](./architecture/hld.md)).

## ADR-001: Без очереди фоновых задач в Фазе 0

**Дата:** 2026-09-03. **Статус:** принято.

**Контекст:** Sectr использует Redis/Asynq и отдельный worker-процесс, потому что обработка GPX — тяжёлый асинхронный пайплайн.

**Решение:** в Фазе 0 нет очереди и нет `backend-worker`. LLM-классификация тактики (4 героя, ~1–3 сек каждая) выполняется синхронно в рамках HTTP-запроса.

**Почему:** нет тяжёлого пайплайна, который нужно снять с request-цикла — YAGNI. Очередь добавляет операционную сложность (ещё один процесс, ещё одна инфраструктурная зависимость) без измеримой выгоды на масштабе школьного пилота.

**Пересмотр:** если пилот покажет заметные задержки или нагрузку — тогда, не заранее. Путь миграции описан в [HLD-спеке](./superpowers/specs/2026-09-03-battle-script-hld-design.md#архитектура).

## ADR-002: Авторизация через код класса, без OAuth/email

**Дата:** 2026-09-03. **Статус:** принято.

**Контекст:** Sectr использует Yandex ID OAuth. Пользователи Battle Script Фазы 0 — дети в закрытом школьном пилоте; COPPA/GDPR-K отмечены бизнес-планом как топ-риск.

**Решение:** `PlayerSession` создаётся по коду класса от учителя + никнейму. Никаких email, OAuth, персональных данных за пределами никнейма.

**Почему:** снимает необходимость строить consent-flow для родителей на этапе, где основная задача — доказать, что дети могут написать рабочую тактику, а не построить полноценную систему идентификации.

**Пересмотр:** при расширении пилота за пределы одного класса или запуске Фазы 1 (публичный B2C) — тогда потребуется полноценная идентификация с согласием родителей.

## ADR-003: LLM-провайдер за портом, не прямая зависимость

**Дата:** 2026-09-03. **Статус:** принято.

**Контекст:** бизнес-план считает юнит-экономику на Gemini 2.5 Flash-Lite, но не обязывает к конкретному вендору.

**Решение:** `IntentClassifier` — порт (интерфейс) в домене; конкретный LLM SDK — адаптер в infrastructure-слое. Домен и валидатор (`ValidateIntentClassification`) не знают, какой именно LLM за портом.

**Почему:** независимость от вендора, тестируемость (мок-адаптер вместо реального вызова в тестах), соответствие принципу "LLM — не граница доверия" — валидатор перепроверяет ответ независимо от того, какой адаптер его вернул.

**Статус реализации:** порт как таковой (Go-интерфейс) ещё не написан — написан только контракт данных (`IntentClassification`) и его валидатор. Сам интерфейс `IntentClassifier` и первый адаптер — не начаты.

## ADR-004: Нет миньонов в Фазе 0 — любой "враг" резолвится в босса

**Дата:** 2026-09-03. **Статус:** принято.

**Контекст:** словарь селекторов включает `lowest_hp_enemy`/`highest_hp_enemy`, изначально задуманные под будущий контент с несколькими врагами.

**Решение:** в Фазе 0 у каждого боя ровно один враг — босс. `lowest_hp_enemy`, `highest_hp_enemy`, `boss` — все резолвятся в одну и ту же сущность.

**Почему:** три стартовых босса не предполагают миньонов; вводить их сейчас — сложность без сюжетной/игровой необходимости.

**Последствие:** способности вроде `piercing_shot` (бьёт вторую цель "если она есть") в Фазе 0 фактически всегда бьют только основную цель — задокументировано как известное ограничение, не баг.

## ADR-005: Щит поглощает урон раньше HP

**Дата:** 2026-09-03. **Статус:** принято (обнаружено, не спланировано заранее).

**Контекст:** HLD-спека приводит пример «если щит танка падает ниже 30% — отступи», подразумевая, что щит — расходуемый ресурс. Ни HLD, ни спека действий классов явно не описывали механику расхода щита.

**Решение:** входящий урон по герою с ресурсом `shield` сначала списывается со щита, остаток (если он превышает текущий щит) — с HP.

**Почему:** без этого правила щит никогда не уменьшался бы, и условие `self_resource_below(shield, ...)` было бы недостижимо в реальном бою — это вскрыл упавший тест `TestRunBattle_StoneGiantRetreatSavesTank` при разработке, не было замечено на этапе спеки. Задокументировано в [спеке разрешения хода](./superpowers/specs/2026-09-03-battle-turn-resolution-design.md#базовые-ресурсы-героев-иллюстративные) постфактум.

**Урок процесса:** пример из уже одобренной спеки (HLD) не был доведён до полной механики в момент написания HLD — сам механизм поглощения щитом обнаружился только на этапе реализации боевого цикла, тремя спеками позже. При написании следующих спек стоит явно проверять: у каждого числового примера в тексте есть ли механизм, который делает его реальным, а не только тематическим.

**Обнаруженное следствие (2026-09-03, при реализации HTTP-слоя):** поскольку щит не восстанавливается (осознанный non-goal — «не вводить экономику ресурсов» в спеке разрешения хода), герой с правилом вида `self_resource_below(shield, 0.3) -> retreat` отступает **навсегда** после первого срабатывания, а не временно — условие остаётся истинным до конца боя, retreat каждый раз выигрывает по приоритету у любого другого правила. Это вскрыл интеграционный HTTP-тест: канонический пример тактики танка из бизнес-плана и HLD не гарантирует победу над `frost_warden` за 30 ходов именно по этой причине. Не считается багом — прямое, логичное следствие уже принятых решений (щит без реген + `retreat` без встроенного тайм-аута), а не новая ошибка. Требует решения при плейтесте: либо это осознанная механика («отступление — надолго, а не на один ход», чему ребёнка тоже стоит научить), либо нужен реген щита/лимит на длительность `retreated`-статуса — пока не решено, зафиксировано как открытый вопрос, не исправлено кодом.
