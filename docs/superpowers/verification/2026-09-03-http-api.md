# Ручная проверка: HTTP API

Спека: [`2026-09-03-http-api-design.md`](../specs/2026-09-03-http-api-design.md). План: [`2026-09-03-http-api.md`](../plans/2026-09-03-http-api.md).

## Что проверялось

`go run ./cmd/api` на реальном порту, запросы через `curl`, не только `httptest`.

## Найдено при ручной проверке (не поймано юнит-тестами)

`BattleLog`/`BattleResult`/`BattleTurn`/`BattleEvent` в `internal/service/battle_engine.go` были без JSON-тегов — уходили в ответ как `Result`/`BossID` (PascalCase, дефолт Go), тогда как весь остальной контракт API — snake_case (`hero_class`, `boss_id` и т.д.). Юнит-тесты (`httptest`) этого не поймали, потому что декодировали ответ обратно в тот же Go-тип — несоответствие имён полей round-trip'ится незаметно. `curl` с реальным JSON поймал сразу.

**Исправлено:** добавлены явные `json:"..."` теги на все 4 типа, пример JSON в спеке разрешения хода приведён в соответствие фактической форме (`action_type`/`target` вместо вложенного `action{type,target}`, единообразный `target_hp_after`).

**Урок:** для типов, которые пересекают HTTP-границу, JSON-теги — часть контракта, а не деталь реализации; отсутствие тега — тоже баг, даже если Go-тесты его не видят. Стоит проверять это явно при добавлении delivery-слоя над уже существующими доменными типами, а не полагаться только на `httptest`.

## Прогон

```
$ curl -s localhost:8099/healthz
{"status":"ok"}

$ curl -s localhost:8099/api/v1/bosses   # 3 босса, ability_pattern виден в каждой фазе

$ curl -s -X POST localhost:8099/api/v1/tactics/classify -d '{"hero_class":"mage","boss_id":"frost_warden","prompt_text":"используй ледяной шар только в фазе щита босса, в остальное время атакуй слабейшего"}'
# -> 200, confidence: high, ожидаемые правила (boss_phase_is(shielded) -> frost_bolt, always -> basic_attack)

$ curl -s -X POST localhost:8099/api/v1/battles -d '{...4 героя с fixed-intent...}'
# -> HTTP 200, outcome: victory, turns: 24
```

## Статус

Пройдено (после фикса JSON-тегов). `make check` чист. Автоматические тесты (`internal/handler/*_test.go`) покрывают все эндпоинты и коды ошибок; этот ручной прогон — дополнительная проверка реальной сериализации по сети, которую httptest-тесты в Go процессе не гарантируют.
