# HLD-дизайн Battle Script

## Краткое описание

Battle Script — веб-автобаттлер для детей 8–16 лет, в котором постоянный состав героев (танк, лучник, маг, целитель и другие классы) сталкивается со сменяющейся чередой боссов. Вместо нажатия «атаки» ребёнок пишет простым языком тактику для каждого героя; LLM переводит эту фразу в закрытый, заранее спроектированный набор действий и условий (Вариант Б из бизнес-плана), а бой разыгрывается детерминированным игровым движком. Продукт учит формулировать намерение точно — это и есть prompt-инжиниринг, поданный как игровой навык.

Фаза 0 (текущий скоуп): закрытый прототип для школьного пилота (2–3 класса), одна платформа — веб. 4 стартовых класса героев, 3 босса, PvE (постоянная команда игрока против боссов, без PvP/рейтинга).

Утверждённая архитектура: монорепозиторий с верхнеуровневыми директориями `backend/` и `web/`, модульный Go backend (Gin, three-layer architecture), синхронная (без очереди задач) обработка LLM-классификации намерений, PostgreSQL как канонический стор, React/TypeScript SPA на фронтенде.

## Цели

- Дать первую версию боевого цикла: ребёнок пишет тактику → видит распознанное ИИ намерение до начала боя → детерминированный бой разыгрывается → результат и прогресс сохраняются.
- Гарантировать честность и воспроизводимость: одинаковый промпт при одинаковом состоянии боя даёт одинаковый исход (обязательное условие для будущего рейтинга).
- Заложить модерацию свободного текста от детей как обязательный этап до LLM-вызова, а не доработку после пилота.
- Не привязываться намертво к одному LLM-провайдеру — вызов классификации намерений идёт через порт, а не напрямую через SDK конкретного вендора.
- Не собирать персональные данные детей в Фазе 0 — авторизация через код класса + никнейм, без OAuth и без email.
- Документировать решения, допущения и открытые вопросы в Markdown, как это делалось в предыдущем проекте (Sectr).

## Не-цели

- Не строить PvP/рейтинговый режим в Фазе 0 — только PvE против боссов.
- Не делать мобильные клиенты в Фазе 0 — только веб.
- Не реализовывать Вариант А (свободная LLM-импровизация исхода боя) в основном боевом цикле — только в возможном будущем несоревновательном песочном режиме, вне скоупа Фазы 0.
- Не вводить очередь фоновых задач (Redis/Asynq и аналоги) — LLM-классификация происходит синхронно в рамках запроса; вернуться к этому решению, только если пилот покажет измеримую потребность (задержки, нагрузка), а не заранее.
- Не строить школьное B2B-лицензирование и биллинг — это Фаза 2 по бизнес-плану.
- Не собирать email/OAuth-идентификацию детей — вне скоупа Фазы 0.
- Не жёстко фиксировать конкретного LLM-вендора в доменном коде.

## Архитектура

Backend — модульный монолит, один процесс на Фазу 0:

- `backend-api` предоставляет REST/OpenAPI для веб-клиента через Gin.

В отличие от Sectr, отдельный worker-процесс в Фазе 0 не нужен: нет тяжёлого асинхронного пайплайна (нет парсинга файлов, нет геообработки) — вся обработка одного боевого хода укладывается в синхронный HTTP-запрос с таймаутом. Если пилот покажет, что LLM-вызовы создают заметную задержку или нагрузку, выделение `backend-worker` с очередью — предусмотренный, но не реализуемый заранее путь миграции.

Backend придерживается трёхслойной архитектуры: `delivery`, `application/domain`, `infrastructure` — как и в Sectr. Зависимости направлены внутрь, к доменным правилам; доменный код не знает про HTTP, SQL или конкретный LLM SDK.

Будущие service boundaries документируются вокруг:

- `moderation` (фильтрация свободного текста);
- `intent-classification` (LLM-порт и адаптеры);
- `battle-engine` (детерминированная симуляция);
- `progression` (достижения, история).

## Компоненты

- **Web App**: React + TypeScript SPA (Vite). Вход по коду класса + никнейм, экран команды героев, ввод тактики текстом для каждого героя, экран «распознанного намерения» до боя, воспроизведение боя по ходам, история боёв, достижения.
- **Backend API**: Gin-based API, проверка кода класса, app-owned сессии, валидация, оркестрация модерации → классификации → симуляции, persistence, чтение статусов/истории.
- **ModerationModule**: фильтрует свободный текст ребёнка до того, как он попадёт в LLM (профанити, попытки ввода PII, злоупотребления). Блокирующий этап, а не постобработка.
- **IntentClassifier (порт)**: принимает текст тактики + контекст класса героя (доступные способности, цели, пороги, фазы босса) и возвращает структурированный intent по фиксированной JSON-схеме класса. Не порождает новые числа/исходы — только классифицирует намерение в заранее заданный набор.
- **LLM Adapter (Gemini 2.5 Flash-Lite, дефолт)**: первая конкретная реализация порта `IntentClassifier`. Возможна замена на другой адаптер (например, Claude Haiku) без изменения домена.
- **BattleEngine**: детерминированный движок симуляции по ходам. Принимает состав игрока с распознанными intent'ами и скрипт босса (фиксированные способности, пороги фаз, скриптованные реплики-провокации), производит `BattleLog` пошагово.
- **PostgreSQL**: каноническое хранилище — герои, боссы, классы, сессии игроков, история боёв, достижения, события модерации.
- **ProgressionModule**: достижения, история, простая статистика по классу/когорте пилота.

Go-код backend придерживается [Uber Go Style Guide](https://github.com/uber-go/guide/blob/master/style.md), как и в Sectr. Makefile содержит цели `fmt`, `lint`, `vet`, `test`, `check`.

## Доменная модель

Центральный агрегат — `BattleSession`.

Основные сущности:

- `ClassroomCohort` — школьный класс/группа пилота (без персональных данных о ребёнке за пределами никнейма);
- `PlayerSession` — сессия ребёнка внутри когорты, привязана к никнейму и коду класса, не к email/OAuth-идентичности;
- `HeroClass` — класс героя с фиксированными пассивками, набором способностей и условий их применения;
- `HeroRoster` — команда из 4 героев, закреплённая за игроком;
- `Boss` — определение босса: HP, фазы, пороги смены фазы, скриптованные способности, флейвор-провокации;
- `PromptSubmission` — сырой текст тактики, который ребёнок написал для конкретного героя перед боем;
- `ModerationEvent` — результат проверки `PromptSubmission` (пройдено/отклонено/причина), хранится отдельно от финального intent;
- `IntentClassification` — структурированный результат перевода текста в закрытый набор действий (приоритет цели, порог отступления, условие каста и т.д.), связан с конкретным `PromptSubmission` и версией схемы класса героя;
- `BattleSession` — конкретный бой: состав игрока с их `IntentClassification`, выбранный `Boss`, статус (в процессе/завершён/ошибка);
- `BattleTurn` / `BattleLog` — пошаговый детерминированный след симуляции: кто на кого подействовал, почему (по какому условию), с каким исходом;
- `BattleResult` — итог боя (победа/поражение), используется для прогресса и ачивок;
- `Achievement` — начисляется по правилам на основе истории `BattleResult`.

`IntentClassification` хранится отдельно от `PromptSubmission`, потому что первое — версионируемый (по схеме класса героя) результат перевода, второе — неизменяемый сырой ввод; это разделение позволяет пересчитать классификацию при обновлении схемы класса без потери исходного текста, аналогично тому, как Sectr хранит raw track отдельно от cleaned track.

## Поток данных

```text
Web App
  -> вход по коду класса + никнейм, создаётся PlayerSession
  -> показывает HeroRoster и выбранного Boss
  -> ребёнок пишет PromptSubmission для каждого героя в ростере
  -> отправляет батч тактик на backend

Backend API
  -> ModerationModule проверяет каждый PromptSubmission
     -> при отклонении: возвращает ошибку с объяснением, LLM не вызывается
  -> IntentClassifier (LLM Adapter) переводит текст в IntentClassification
     по закрытой JSON-схеме класса героя
     -> при невалидном/просроченном ответе: один retry
     -> при повторной неудаче: детерминированный fallback-intent
        с пометкой "не поняли однозначно" (часть обучающего цикла)
  -> API возвращает распознанные IntentClassification для показа игроку
     ДО начала боя (ключевое обучающее требование бизнес-плана)

Web App
  -> показывает распознанное намерение по каждому герою
  -> ребёнок подтверждает состав тактик

Backend API
  -> BattleEngine детерминированно разыгрывает BattleSession по ходам
     на основе IntentClassification и скрипта Boss
  -> сохраняет BattleLog, BattleResult
  -> ProgressionModule обновляет Achievement

Web App
  -> воспроизводит BattleLog по ходам
  -> показывает результат, историю, достижения
```

## Модерация и безопасность (Trust & Safety)

Это заблокированное условие готовности к пилоту, а не доработка после запуска — так зафиксировано в бизнес-плане (§5, риск «Безопасность детей и соответствие требованиям»).

- Свободный текст ребёнка проходит `ModerationModule` до того, как попадёт в любой LLM-вызов.
- `PlayerSession` не содержит персональных данных за пределами никнейма и кода класса — сознательный архитектурный выбор для Фазы 0, снимающий часть COPPA/GDPR-K риска без необходимости строить полноценный consent-flow для родителей на этапе закрытого пилота.
- Логи `PromptSubmission` и `ModerationEvent` хранятся с ограниченным сроком жизни; сырые тексты не попадают в общую observability/метрики без маскирования.
- `IntentClassifier` работает только в режиме классификации в закрытый набор действий — открытая генерация текста в бою (Вариант А) не используется в Фазе 0 ни для расчёта урона, ни для исходов.

## Обработка ошибок

- Отклонённый `ModerationEvent` останавливает конвейер до LLM — ребёнку показывается объяснение и предлагается переформулировать.
- Таймаут или невалидный по схеме ответ LLM-адаптера — один retry с тем же промптом.
- Повторная неудача — детерминированный fallback-intent (например, «атаковать цель с наименьшим HP»), явно помеченный игроку как "нечёткая интерпретация" — по бизнес-плану это часть обучающего цикла, а не деградация, которую нужно скрывать.
- `BattleEngine` не начинает симуляцию, пока не получены `IntentClassification` для всех героев ростера — частичные составы не разыгрываются.
- Все внешние вызовы (LLM adapter) обёрнуты портом с чётким интерфейсом ошибок, чтобы retry/fallback-логика жила в domain-слое, а не в конкретном адаптере.

## Тестирование и валидация

- `BattleEngine` — unit- и property-тесты на детерминированность: одинаковый вход (ростер + intent'ы + состояние босса) должен всегда давать одинаковый `BattleLog`. Это гарант честности будущего рейтинга (§5 бизнес-плана).
- `IntentClassifier` — eval-датасет из реальных детских формулировок тактик с ожидаемым intent на каждую; прогон адаптера против датасета — часть CI, а не разовая ручная проверка.
- `ModerationModule` — тесты на известные классы проблемного ввода (профанити, попытки PII, промпт-инъекции, пустой/бессмысленный текст).
- Интеграционный тест полного пути: `PromptSubmission` → модерация → классификация (с моком LLM-адаптера) → симуляция → `BattleResult`.
- HLD должен проверяться через архитектурное ревью границ модулей и ревью data model на разделение raw (`PromptSubmission`), классифицированного (`IntentClassification`) и агрегированного (`BattleResult`) состояния — по аналогии с разделением raw/cleaned/aggregate в Sectr.

## Открытые вопросы и допущения

- Допущение: Фаза 0 не включает PvP/рейтинг — если это неверно, `BattleEngine` и `IntentClassifier`-контракт всё равно не меняются (они уже детерминированы по конструкции), но потребуется добавить matchmaking и синхронизацию между двумя `PlayerSession`.
- LLM-провайдер по умолчанию — Gemini 2.5 Flash-Lite (совпадает с оценкой стоимости в бизнес-плане); порт `IntentClassifier` рассчитан на замену адаптера без изменения домена.
- Точная JSON-схема действий на класс героя (танк/лучник/маг/целитель) не зафиксирована в этом документе — она специфична для геймдизайна каждого класса и должна прийти отдельной, более узкой спекой перед реализацией `BattleEngine`.
- Формат демонстрации "распознанного намерения" в UI (текстом/иконками/таймлайном) — вопрос UX, не архитектуры; не блокирует этот HLD.
