# HTTP API — дизайн

## Краткое описание

Первый HTTP-слой поверх уже реализованного и протестированного доменного ядра (`internal/service`): раскрытие контента боссов, прогон тактики через модерацию+классификацию для показа ребёнку «распознанного намерения» до боя (обучающий крючок из HLD), и запуск самого боя. Без персистентности и без авторизации — оба явно вне скоупа (см. HLD и `backend/README.md`). Это делает API стейтлес: клиент присылает всё нужное в каждом запросе, backend ничего не хранит между вызовами. Это осознанное временное упрощение, не архитектура на вырост — как только появится `PlayerSession`/персистентность, `POST /api/v1/battles` перестанет требовать intent'ы в теле запроса (они будут читаться из сохранённого состояния).

## Цели

- Дать Gin-based `delivery`-слой (уже зафиксировано в HLD), тонкий: валидация HTTP-входа, вызов доменных функций, сериализация ответа — без бизнес-логики в handler'ах.
- 4 эндпоинта: список/детали боссов (контент), классификация тактики, запуск боя, health-check.
- Использовать существующий пайплайн (`BasicModerator` → `ClassifyWithFallback` → `LocalHeuristicClassifier` → `ValidateIntentClassification` → `RunBattle`) без изменений в domain-слое.

## Не-цели

- Не вводить персистентность, авторизацию, `PlayerSession`/`ClassroomCohort` в этом шаге — уже зафиксировано как отдельная будущая работа.
- Не вводить `/readyz` — сейчас нет внешних зависимостей (БД, кэш), которые имело бы смысл проверять; добавится вместе с персистентностью, а не как заглушка сейчас.
- Не подключать реальный LLM — сервер продолжает использовать `LocalHeuristicClassifier`, как и весь пайплайн до сих пор.

## Эндпоинты

| Метод | Путь | Тело запроса | Ответ |
|---|---|---|---|
| `GET` | `/healthz` | — | `200 {"status":"ok"}` |
| `GET` | `/api/v1/bosses` | — | `200` список боссов (id, display_name, фазы: id/порог/провокация/ability_pattern) |
| `GET` | `/api/v1/bosses/{boss_id}` | — | `200` один босс тем же форматом, `404` если нет такого `boss_id` |
| `POST` | `/api/v1/tactics/classify` | `{hero_class, boss_id, prompt_text}` | `200 IntentClassification` \| `422` при отклонении модерацией \| `404` при неизвестном `boss_id`/`hero_class` |
| `POST` | `/api/v1/battles` | `{boss_id, heroes: [{id, hero_class, intent: IntentClassification}]}` | `200 BattleLog` \| `422` если хотя бы один `intent` не проходит `ValidateIntentClassification` \| `404` при неизвестном `boss_id` |

Контент боссов в `GET /api/v1/bosses*` намеренно включает `ability_pattern` (сырые строки вроде `"cleave_all"`) — это прямая реализация «правила честности» из спеки боссов: всё, на что может ссылаться условие в тактике, должно быть видно игроку до её написания.

## Обработка ошибок

- Неизвестный `boss_id`/`hero_class` во входе — `404`, единый формат ошибки `{"error": "<код>", "message": "<человекочитаемо>"}`.
- Отклонение модерацией — `422`, `{"error": "moderation_rejected", "message": "<ModerationResult.Reason>"}`, `IntentClassifier` не вызывается (проверяется существующим `BasicModerator` до вызова `ClassifyWithFallback` — это дисциплина вызывающего кода в handler'е, как и было спроектировано в предыдущей спеке).
- Невалидный `intent` в `POST /api/v1/battles` — `422` с текстом ошибки от `ValidateIntentClassification`, бой не запускается вообще (частичный ростер не разыгрывается — как и в HLD).
- Все остальные непредвиденные ошибки — `500` с общим сообщением, без утечки внутренних деталей в тело ответа.

## Тестирование и валидация

- `httptest`-тесты на каждый эндпоинт: happy path + каждый описанный код ошибки.
- Интеграционный тест на весь HTTP-путь: `POST /tactics/classify` → взять результат → `POST /battles` с ним → получить `BattleLog` с `victory` — HTTP-версия уже существующего `TestFullPipeline_TextToAction`, но через реальные HTTP-запросы, не прямые вызовы Go-функций.
- Ручной прогон (`docs/superpowers/verification/`) — после этого шага в проекте впервые появляется что-то, что можно руками проверить curl'ом; первая запись в verification-логе идёт сюда же.

## Открытые вопросы

- Формат ошибок (`{"error", "message"}`) — минимальный рабочий контракт, не финализирован под конкретный фронтенд-фреймворк; может измениться, когда появится `web/`.
- `POST /api/v1/battles` принимает клиентский `intent` без проверки, что он был получен именно через `/tactics/classify` этого же сервера (стейтлес-дизайн этого шага такое не гарантирует) — приемлемо, потому что `ValidateIntentClassification` всё равно перепроверяет каждое поле; закрывается полностью только с появлением `PlayerSession`/персистентности, когда classify-результат будет привязываться к серверной сессии, а не приходить от клиента заново.
