# Схема действий классов героев — дизайн

## Краткое описание

Эта спека уточняет [`2026-09-03-battle-script-hld-design.md`](./2026-09-03-battle-script-hld-design.md): фиксирует закрытый словарь условий, селекторов целей и способностей для 4 стартовых классов героев, и конкретную JSON-схему `IntentClassification`, в которую `IntentClassifier` обязан переводить свободный текст ребёнка. Без этой схемы нельзя ни писать промпт для LLM-адаптера, ни реализовывать `BattleEngine`.

Ключевой принцип из бизнес-плана сохранён буквально: LLM классифицирует намерение в закрытый набор, никогда не придумывает новые числа или исходы. Механика по форме близка к Gambit-системе Final Fantasy XII (упорядоченный список «условие → действие», исполняемый по приоритету каждый ход) — это проверенный, понятный игрокам паттерн для выражения условной тактики без написания кода.

## Цели

- Дать одну общую структуру «Tactic Program» (упорядоченный список правил `условие → действие`), одинаковую по форме для всех классов, чтобы `BattleEngine` и `IntentClassifier` работали с единым контрактом.
- Зафиксировать закрытый словарь условий и селекторов целей, общий для всех классов.
- Зафиксировать закрытый словарь способностей на класс героя (4 старта: Танк, Лучник, Маг, Целитель).
- Определить, что фиксировано (пассивки класса) и что промптуется (условия, приоритет цели, пороги) — по принципу из HLD.
- Дать пример конкретной JSON-схемы `IntentClassification`, готовой для server-side валидации ответа LLM.

## Не-цели

- Не балансировать финальные числа урона/лечения/порогов — все числовые значения в этой спеке иллюстративные и требуют плейтеста; это игродизайнерская работа, а не архитектурная.
- Не поддерживать в Фазе 0 кросс-геройские условия («если танк отступил — маг тоже отступает») — каждая `Tactic Program` героя классифицируется и исполняется независимо. Явное упрощение ради детерминизма и параллельной классификации.
- Не поддерживать произвольную длину списка правил — вводится потолок в 3 правила на героя (см. «Валидация»).
- Не вводить обучаемый/адаптивный ИИ босса — скрипт босса такой же закрытый и детерминированный, как и герои.

## Общая структура: Tactic Program

Каждый герой в бою имеет `TacticProgram` — упорядоченный список правил:

```text
TacticProgram := [Rule, ...]  (максимум 3)
Rule := { condition: Condition, action: Action }
```

Каждый ход `BattleEngine` проходит правила героя по порядку `priority` (0 — высший) и исполняет действие первого правила, чей `condition` истинен на текущий момент хода. Если ни одно правило не сработало (или список пуст из-за fallback, см. «Обработка ошибок»), исполняется `fallback_action` — фиксированный дефолт по классу, не зависящий от LLM.

Это прямое соответствие примеру из бизнес-плана:

```text
ТАНК: держи передний край, провоцируй босса каждый раз, когда он целится
      в целителя, и если щит падает ниже 30% — отступи на ряд назад.

→ [priority 0] condition: boss_targeting(role=healer)  → action: taunt(self)
  [priority 1] condition: self_resource_below(shield, 0.3) → action: retreat(self)
  [priority 2] condition: always → action: basic_attack(lowest_hp_enemy)
```

## Словарь условий (Conditions)

Общий для всех классов, закрытый набор:

| Тип условия | Параметры | Смысл |
|---|---|---|
| `always` | — | Безусловный catch-all, обычно последнее правило |
| `self_resource_below` | `resource: hp\|shield\|mana`, `threshold: 0.0–1.0` | Собственный ресурс героя ниже порога |
| `ally_resource_below` | `target: TargetSelector`, `resource`, `threshold` | Ресурс союзника (по селектору) ниже порога |
| `boss_resource_below` | `resource: hp\|shield`, `threshold: 0.0–1.0` | Ресурс босса ниже порога |
| `boss_phase_is` | `phase_id: string` | Босс находится в конкретной, заранее раскрытой фазе |
| `boss_targeting` | `target: TargetSelector` | Босс в этот ход целится в героя/роль, заданную селектором |
| `ally_status_is` | `target: TargetSelector`, `status: string` | У союзника активен статус-эффект (оглушение, дебафф и т.п.) |

Пороги (`threshold`) — числа с плавающей точкой в диапазоне `[0.0, 1.0]`, сервер отклоняет любое значение вне диапазона независимо от того, что вернула LLM.

## Словарь селекторов целей (TargetSelector)

Закрытый набор, общий для условий и действий:

| Селектор | Смысл |
|---|---|
| `self` | Сам герой |
| `lowest_hp_enemy` | Враг (в бою Фазы 0 — только босс, либо его призванные существа, если такие есть у конкретного босса) с наименьшим текущим HP |
| `highest_hp_enemy` | Враг с наибольшим текущим HP |
| `lowest_hp_ally` | Союзник (включая себя) с наименьшим текущим HP |
| `role:<hero_class>` | Конкретная роль в команде, например `role:healer`, `role:tank` |
| `boss` | Явно босс, а не его миньоны (когда нужно отличить от `highest_hp_enemy`) |

Если селектор не резолвится (например, `role:healer`, а целителя нет в текущем ростере) — правило считается неприменимым в этот ход, `BattleEngine` переходит к следующему правилу по приоритету, как при ложном `condition`.

Детерминизм: словарь не включает `random_*` селекторы в Фазе 0. Если в будущем понадобится случайность (например, у босса), она должна быть по seed, привязанному к `BattleSession.id`, чтобы бой оставался воспроизводимым — это прямое требование к честности из HLD, а не новая механика в этой спеке.

## Классы героев: способности и фиксированные пассивки

Пассивка каждого класса **не промптуется** — фиксированное игровое правило, вокруг которого ребёнок строит тактику (принцип «Пассивные черты против авторских действий» из бизнес-плана). Числа ниже иллюстративные, требуют плейтеста.

### Танк

- **Пассивка (фикс.):** +5% урона за каждый последовательный ход на передней линии; сбрасывается при `retreat`.
- **Способности (промптуемая цель/условие, не промптуемый эффект):**
  - `basic_attack(target)` — базовая атака.
  - `taunt(target_context)` — на этот ход весь урон босса по указанной роли/герою перенаправляется на танка.
  - `retreat(self)` — уходит в тыл, снижает шанс быть целью босса в следующий ход, сбрасывает пассивку.

### Лучник

- **Пассивка (фикс.):** +10% шанс крита по целям ниже 30% HP.
- **Способности:**
  - `basic_attack(target)`.
  - `piercing_shot(target)` — попадает по цели и следующему по HP врагу за ней.
  - `aimed_shot(target)` — усиленный одиночный урон, более долгий откат (кулдаун — фиксированные игровые данные, не промптуются).

### Маг

- **Пассивка (фикс.):** +15% урона от заклинаний во время смены фазы босса.
- **Способности:**
  - `basic_attack(target)`.
  - `frost_bolt(target)` — из примера бизнес-плана: бонусный урон по целям с активным щитом.
  - `fireball(target)` — урон по области вокруг цели.

### Целитель

- **Пассивка (фикс.):** автоматический +20% к лечению союзника с наименьшим текущим HP (снижает цену ошибки в выборе цели).
- **Способности:**
  - `heal(target)`.
  - `cleanse(target)` — снимает один дебафф-статус.
  - `basic_attack(target)` — низкоприоритетный fallback-урон.

Кулдауны, стоимость маны и точные величины урона/лечения — фиксированные игровые данные способности, не часть `IntentClassification`; ребёнок управляет **условием и целью**, не числами.

## Схема `IntentClassification` (JSON)

```json
{
  "hero_class": "mage",
  "schema_version": "2026-09-03.1",
  "rules": [
    {
      "priority": 0,
      "condition": { "type": "boss_phase_is", "phase_id": "shield" },
      "action": { "type": "frost_bolt", "target": "lowest_hp_enemy" }
    },
    {
      "priority": 1,
      "condition": { "type": "always" },
      "action": { "type": "basic_attack", "target": "lowest_hp_enemy" }
    }
  ],
  "fallback_action": { "type": "basic_attack", "target": "lowest_hp_enemy" },
  "source_prompt_submission_id": "uuid",
  "confidence": "high"
}
```

`confidence` принимает `high` (LLM уверенно распознала намерение по схеме) или `low_fallback_used` (сработал retry/fallback путь из HLD) — используется UI, чтобы показать ребёнку пометку «не поняли однозначно» именно тогда, когда это действительно произошло.

## Валидация (server-side, не доверяем LLM вслепую)

Даже если промпт LLM уже ограничивает её словарём класса, backend обязан провалидировать ответ независимо — LLM-провайдер не является границей доверия:

- `hero_class` соответствует герою, для которого шёл запрос.
- Каждый `action.type` входит в закрытый список способностей `hero_class`.
- Каждый `condition.type` входит в общий словарь условий.
- Каждый `target` (в условии и в действии) входит в словарь селекторов, допустимых для этого `action.type`/`condition.type`.
- `threshold` — число в `[0.0, 1.0]`.
- `rules` — не более 3 элементов, `priority` уникальны и по порядку от 0.
- `phase_id` в `boss_phase_is` существует в скрипте текущего `Boss`.
- Ответ, не прошедший валидацию, обрабатывается так же, как невалидный/просроченный ответ LLM в HLD: один retry, затем fallback с `confidence: low_fallback_used`.

## Контракт LLM-классификатора

`IntentClassifier` формирует запрос к LLM-адаптеру из:

- свободного текста `PromptSubmission` (уже прошедшего модерацию);
- закрытого словаря условий/селекторов/способностей, доступных для `hero_class` данного героя, с человекочитаемыми описаниями каждого элемента;
- текущего раскрытого игроку контекста босса (фазы, пороги, поведенческие подсказки) — того же самого, что видел ребёнок перед написанием тактики, чтобы условия вроде `boss_phase_is` были осмысленны;
- инструкции вернуть ответ строго по JSON-схеме выше.

LLM не получает доступа к текущему live-состоянию боя (HP игроков в реальном времени и т.п.) — только к статичному контексту, известному до начала боя. Это специально: `IntentClassification` формируется один раз до боя (по дизайну из HLD — «ребёнок подтверждает» после показа распознанного намерения), а не пересчитывается на лету по ходам.

## Минимальный контракт скрипта босса

Эта спека не проектирует полный `Boss` (это отдельная работа), но фиксирует минимум, необходимый для условий выше:

- `phases: [{ phase_id, hp_threshold_enter, fixed_ability_pattern }]` — упорядоченный список фаз с порогом HP входа.
- Все `phase_id` босса раскрываются игроку до начала боя (совпадает с «перед каждым боем раскрываются сильные и слабые стороны босса» из бизнес-плана) — иначе условие `boss_phase_is` было бы нечестным по отношению к ребёнку.
- Поведение босса по фазам — такой же закрытый, детерминированный скрипт, как и `TacticProgram` героя; не LLM-управляемое в Фазе 0.

## Обработка ошибок

Наследует и уточняет раздел HLD:

- Невалидный по этой схеме ответ LLM (незнакомый `action.type`/`condition.type`/`target`, threshold вне диапазона, больше 3 правил, неизвестный `phase_id`) трактуется как невалидный ответ — retry, затем fallback.
- `fallback_action` определён на уровне класса героя (не на уровне конкретного боя), поэтому он всегда доступен даже при полном отказе LLM-адаптера.
- Нерезолвящийся `target` в конкретный момент хода — не ошибка классификации, а штатный переход к следующему правилу по приоритету (см. «Словарь селекторов»).

## Тестирование и валидация

- Golden-тесты валидатора: набор заведомо валидных и невалидных `IntentClassification` JSON на каждый класс, включая пограничные случаи (threshold = 0 и 1, 3 правила, неизвестный `phase_id`).
- Eval-датасет `IntentClassifier`: реальные детские формулировки тактик (собрать во время школьного пилота) → ожидаемый `TacticProgram` — расширяет eval-датасет из HLD.
- Property-тест `BattleEngine`: для любого валидного `TacticProgram` и скрипта босса симуляция детерминирована (одинаковый вход → побайтово одинаковый `BattleLog`).
- Тест на нерезолвящийся селектор: правило с `role:healer` при отсутствии целителя в ростере корректно пропускается в пользу следующего правила.

## Открытые вопросы

- Числовые значения пассивок и способностей — плейсхолдеры, нужен плейтест-проход с игровым дизайнером/вами перед фиксацией в коде.
- Ограничение в 3 правила на героя — начальная гипотеза ради простоты понимания LLM и ребёнком; можно пересмотреть после пилота, если 3 правил не хватает для интересной тактики.
- Не решено: показывать ли ребёнку весь JSON `IntentClassification` буквально, или переводить его обратно в человекочитаемое предложение в UI («Танк будет провоцировать босса, когда он целится в целителя») — вопрос UX, не блокирует эту спеку, но влияет на web-клиент.
