# Скрипт боссов Фазы 0 — дизайн

## Краткое описание

Уточняет «Минимальный контракт скрипта босса» из [`2026-09-03-hero-class-action-schema-design.md`](./2026-09-03-hero-class-action-schema-design.md): фиксирует структуру `Boss`/`BossPhase` и описывает 3 стартовых босса для школьного пилота. Каждый босс спроектирован так, чтобы обучать конкретному классу условий из словаря — это прямая реализация «обучающего крючка» из бизнес-плана: неоднозначно написанный промпт должен проигрывать боссу именно из-за той механики, которую этот босс тестирует.

Как и в HLD, поведение босса — фиксированный, детерминированный скрипт, не LLM-управляемый в Фазе 0. Провокации (флейвор-текст) — единственное место, где в будущем допустим Вариант А (свободная LLM-генерация), потому что это текст, а не исход боя; в Фазе 0 провокации тоже фиксированный текст, без LLM.

## Цели

- Зафиксировать структуру `Boss` и `BossPhase`, совместимую с условиями `boss_phase_is`, `boss_resource_below`, `boss_targeting` из схемы действий.
- Дать 3 конкретных босса для Фазы 0, каждый нацеленный на свой обучающий момент.
- Зафиксировать, что именно раскрывается игроку до боя (по принципу честности из HLD: условие не может ссылаться на скрытую от ребёнка информацию).

## Не-цели

- Не проектировать полную библиотеку боссов Фазы 1+ — только 3 старта.
- Не давать боссу способность целиться по LLM-логике — таргетинг босса такой же фиксированный скрипт, как и всё остальное в Фазе 0.
- Не балансировать точные числа урона/HP — иллюстративные, требуют плейтеста.

## Структура `Boss` / `BossPhase`

```json
{
  "boss_id": "frost_warden",
  "display_name": "Ледяной страж",
  "max_hp": 1000,
  "phases": [
    {
      "phase_id": "exposed",
      "hp_threshold_enter": 1.0,
      "ability_pattern": ["cleave_all", "single_target_hit"],
      "provocation": "«Подходите, если смелости хватит!»"
    },
    {
      "phase_id": "shielded",
      "hp_threshold_enter": 0.6,
      "ability_pattern": ["shield_up", "single_target_hit"],
      "provocation": "«Мой щит вас не пропустит!»"
    },
    {
      "phase_id": "enraged",
      "hp_threshold_enter": 0.25,
      "ability_pattern": ["cleave_all", "cleave_all", "single_target_hit"],
      "provocation": "«Хватит! Никто не уйдёт!»"
    }
  ]
}
```

`hp_threshold_enter` — доля максимального HP босса, при пересечении которой (сверху вниз) начинается фаза; фазы упорядочены от `1.0` вниз, `BattleEngine` переключает `phase_id` в тот момент, когда `boss.hp / boss.max_hp` опускается ниже порога следующей фазы. `ability_pattern` — фиксированный, циклически повторяющийся список действий босса по ходам (не LLM, не рандом в Фазе 0).

**Правило честности:** все `phases` (id, пороги входа, паттерн способностей в общих чертах — "бьёт по площади" / "ставит щит" — и `provocation`) раскрываются игроку **до** написания тактики, в том же экране, что показывает ростер. Условие `boss_phase_is` в `TacticProgram` не может ссылаться на информацию, которую ребёнок не видел — иначе обучающий цикл ломается на нечестности, а не на сложности формулировки.

## 3 стартовых босса

### 1. Ледяной страж (`frost_warden`) — учит тайминг по фазе

Тестирует условие `boss_phase_is`. Ставит щит во второй фазе (`shielded`), поглощающий часть обычного урона — но именно в этой фазе усилен урон `frost_bolt` мага (пример из бизнес-плана). Промпт мага «атакуй всегда сильнейшей атакой» проигрывает по эффективности промпту «используй ледяной шар только в фазе щита, иначе — базовая атака», хотя оба варианта выглядят разумными до объяснения механики.

- Фазы: `exposed` (1.0–0.6) → `shielded` (0.6–0.25) → `enraged` (0.25–0)`.
- Обучает: `boss_phase_is`, специфичные для фазы способности (`frost_bolt` мага).

### 2. Охотник теней (`shadow_hunter`) — учит защиту роли

Тестирует условие `boss_targeting`. С фазы `hunting` этот босс явно нацеливается на целителя каждый второй ход (видно игроку заранее в описании босса — «Охотник всегда преследует лекаря»). Промпт танка без правила `boss_targeting(role=healer) → taunt` регулярно теряет целителя рано, что делает весь остаток боя намного тяжелее — наглядно показывает цену отсутствия защитного условия.

- Фазы: `stalking` (1.0–0.5, целится по случайному герою низкого HP — детерминированно по `lowest_hp_ally` эквиваленту, не рандом) → `hunting` (0.5–0, целится по роли `healer` явно).
- Обучает: `boss_targeting`, `taunt`.

### 3. Каменный великан (`stone_giant`) — учит порог отступления

Тестирует условие `self_resource_below` + `retreat`. В фазе `crumbling` наносит нарастающий урон по фронтальному герою, но резко теряет урон по герою, ушедшему в `retreat`. Промпт танка без правила «если HP/щит ниже X% — отступи» стабильно теряет танка до конца фазы; с правилом — герой успевает выйти вовремя.

- Фазы: `steady` (1.0–0.4, стандартный урон) → `crumbling` (0.4–0, нарастающий урон по фронту, на манер business-plan примера «щит падает ниже 30% — отступи»).
- Обучает: `self_resource_below`, `retreat`.

## Обработка ошибок

- `BattleEngine` не может создать `BattleSession` со скриптом босса, у которого `phases` не покрывают `[0, 1.0]` без пропусков или с непоследовательными порогами — это ошибка конфигурации контента, а не времени выполнения; проверяется на этапе загрузки/сида данных, до старта боя.
- Если бой длится дольше разумного числа ходов (защита от зависшего состояния при некорректной комбинации правил и паттерна босса) — `BattleEngine` принудительно завершает `BattleSession` со статусом `aborted` (см. `BattleResult.Outcome` в [спеке разрешения хода](./2026-09-03-battle-turn-resolution-design.md#условия-завершения-боя)) и логирует причину; порог числа ходов — фиксированная защитная константа, не игровой баланс.

## Тестирование и валидация

- Тест загрузки контента: все 3 стартовых босса проходят валидацию структуры `phases` (монотонные, непрерывные пороги от 1.0 до 0).
- Property-тест: для каждого босса и каждого класса героя с «наивным» и «правильным» `TacticProgram` (примеры из раздела «3 стартовых босса») симуляция детерминирована и «правильный» промпт статистически не проигрывает «наивному» по числу ходов до победы — этим тестом фиксируется, что designed-обучающий момент действительно работает в движке, а не только на бумаге.
- Тест защитного лимита ходов: заведомо некорректная комбинация правил не приводит к бесконечному циклу.

## Открытые вопросы

- Точные числа урона/HP/порогов по всем 3 боссам — плейсхолдеры, нужен плейтест-проход перед фиксацией в сид-данных.
- Итоговый текст провокаций (`provocation`) — только примеры тона; финальные формулировки — вопрос сценаристики/UX, не архитектуры.
- Способны ли миньоны/призванные существа появляться у какого-либо из 3 боссов — не решено; текущий дизайн предполагает, что в Фазе 0 у босса нет миньонов (`highest_hp_enemy`/`lowest_hp_enemy` резолвятся к самому боссу).
