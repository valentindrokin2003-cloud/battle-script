# Разрешение боевого хода — дизайн

## Краткое описание

Замыкает боевой цикл, оставленный открытым в [HLD](./2026-09-03-battle-script-hld-design.md) и в [схеме действий](./2026-09-03-hero-class-action-schema-design.md): как именно `TacticProgram`, выбранное действие (`SelectAction`, уже реализован и протестирован) и скрипт босса превращаются в урон/лечение, `BattleTurn`-лог и итоговый `BattleResult`. Даёт конкретные, но иллюстративные числа эффектов способностей — без них движок не запустить, но баланс не финален и требует плейтеста, как и все числа в предыдущих спеках.

## Цели

- Зафиксировать таблицу эффектов способностей (урон/лечение) для 4 классов, достаточную для первой играбельной симуляции.
- Зафиксировать порядок хода: сначала все герои (по фиксированному порядку ростера), затем босс.
- Зафиксировать правило таргетинга босса по ходам для каждого из 3 стартовых боссов — в спеке боссов это было явно расписано только для Охотника теней; здесь решение достраивается для двух остальных, специально ради того, чтобы их «обучающий крючок» был механически реален, а не только тематическим текстом.
- Зафиксировать структуры `BattleTurn`, `BattleLog`, `BattleResult` и условия победы/поражения/аварийного завершения.

## Не-цели

- Не вводить экономику маны/кулдаунов в этой итерации — способности применяются без проверки стоимости; ресурс `mana` остаётся в модели данных (для будущих условий/контента), но не расходуется. Явное сужение скоупа, не забытая деталь.
- Не вводить статус-эффекты, накладываемые боссами (`cleanse` у целителя остаётся в словаре, но ни один из 3 боссов Фазы 0 ничего не накладывает — целитель нечем будет "снимать" на этом контенте).
- Не вводить миньонов/несколько врагов — уже зафиксировано в спеке боссов.

## Таблица эффектов способностей (иллюстративная)

| Класс | Способность | Эффект |
|---|---|---|
| Танк | `basic_attack` | 9 урона по цели |
| Танк | `taunt` | Без урона; временно принудительно делает себя целью босса (см. «Таргетинг босса») |
| Танк | `retreat` | Без урона; ставит статус `retreated` на этот ход, снимает пассивку фронтлайна |
| Лучник | `basic_attack` | 10 урона по цели |
| Лучник | `piercing_shot` | 8 урона по цели + 5 урона следующему врагу по HP, если он есть (в Фазе 0 второго врага нет — по факту эквивалентно 8 урона) |
| Лучник | `aimed_shot` | 16 урона по цели |
| Маг | `basic_attack` | 9 урона по цели |
| Маг | `frost_bolt` | 18 урона, если у босса сейчас фаза `shielded`; иначе 5 урона (специально хуже базовой атаки — иначе промпт «всегда ледяной шар» не проигрывал бы, и урок фазового тайминга не работал бы) |
| Маг | `fireball` | 11 урона по всем врагам (в Фазе 0 — эквивалент одиночной цели) |
| Целитель | `basic_attack` | 5 урона по цели |
| Целитель | `heal` | 12 HP цели |
| Целитель | `cleanse` | Снимает один указанный статус у цели, если он есть; иначе не действует |

Фиксированные пассивки (из схемы действий) применяются поверх этой таблицы:
- Танк: +5% урона за каждый последовательный ход на передней линии (сбрасывается при `retreat`).
- Лучник: +10% урона по цели ниже 30% HP.
- Маг: +15% урона в ход смены фазы босса.
- Целитель: +20% к `heal`, если цель — герой с наименьшим текущим HP в отряде (после сработавшего `heal`, не отдельное условие).

## Базовые ресурсы героев (иллюстративные)

| Класс | HP | Щит | Мана |
|---|---|---|---|
| Танк | 120 | 60 | — |
| Лучник | 80 | — | 40 |
| Маг | 70 | — | 50 |
| Целитель | 75 | — | 50 |

Мана присутствует в модели (для условий вида `self_resource_below(mana, ...)`), но не расходуется действиями в этой итерации (см. «Не-цели»).

**Щит поглощает урон раньше HP.** Если у героя есть ресурс `shield`, входящий урон сначала списывается с него и только остаток (если он превышает текущий щит) — с HP. Без этого правила пороговое условие `self_resource_below(shield, ...)` из примера в HLD никогда не срабатывало бы: щит не имеет отдельного источника урона, если урон по умолчанию идёт напрямую по HP.

## Сид-данные боссов Фазы 0 (иллюстративные)

Спека боссов зафиксировала полный `Boss` JSON только для `frost_warden`; здесь дополняются `shadow_hunter` и `stone_giant` тем же уровнем детализации, нужным для запуска движка.

```json
{ "boss_id": "shadow_hunter", "display_name": "Охотник теней", "max_hp": 800,
  "phases": [
    { "phase_id": "stalking", "hp_threshold_enter": 1.0, "ability_pattern": ["single_target_hit"] },
    { "phase_id": "hunting",  "hp_threshold_enter": 0.5, "ability_pattern": ["single_target_hit", "cleave_all"] }
  ]
}
```

```json
{ "boss_id": "stone_giant", "display_name": "Каменный великан", "max_hp": 1200,
  "phases": [
    { "phase_id": "steady",    "hp_threshold_enter": 1.0, "ability_pattern": ["single_target_hit"] },
    { "phase_id": "crumbling", "hp_threshold_enter": 0.4, "ability_pattern": ["single_target_hit", "single_target_hit", "cleave_all"] }
  ]
}
```

Урон `single_target_hit`/`cleave_all` по боссам и фазам (иллюстративный):

| Босс | Фаза | `single_target_hit` | `cleave_all` |
|---|---|---|---|
| `frost_warden` | `exposed` | 12 | 6 (по каждому) |
| `frost_warden` | `shielded` | 12 | — |
| `frost_warden` | `enraged` | 16 | 8 (по каждому) |
| `shadow_hunter` | `stalking` | 10 | — |
| `shadow_hunter` | `hunting` | 14 | 6 (по каждому) |
| `stone_giant` | `steady` | 10 | — |
| `stone_giant` | `crumbling` | 22 | 8 (по каждому) |

## Порядок хода

```text
1. Для каждого героя в ростере (в фиксированном порядке): SelectAction(program, fallback, ctx) -> действие,
   действие применяется немедленно (следующий герой уже видит обновлённое состояние).
2. Босс выбирает действие по своему ability_pattern (циклически, по номеру хода) и по правилу
   таргетинга своего boss_id (см. ниже), действие применяется.
3. BattleEngine проверяет условия победы/поражения/лимита ходов, переходит к следующему ходу или завершает BattleSession.
```

Герои действуют раньше босса каждый ход — это уже подразумевалось примерами в предыдущих спеках (герой реагирует на текущую фазу/таргетинг босса, установленные на предыдущем ходу босса).

## Таргетинг босса по ходам

Общее правило по умолчанию (для боссов, где ниже не сказано иное): целью становится герой с наименьшим текущим HP среди героев без статуса `retreated`; если все герои в `retreated`, целью становится герой с наименьшим HP без исключения.

- **`frost_warden`**: применяет общее правило по умолчанию во всех фазах. Обучающий момент этого босса — про выбор способности мага (см. таблицу эффектов), не про то, кого он бьёт.
- **`shadow_hunter`**: в фазе `stalking` — общее правило по умолчанию. В фазе `hunting` — на чётных номерах хода явно целится в героя с ролью `healer` (если он есть в ростере), на нечётных — общее правило по умолчанию. Раскрывается игроку как «Охотник всегда преследует лекаря» (см. спеку боссов).
- **`stone_giant`**: в фазе `steady` — общее правило по умолчанию. В фазе `crumbling` — целится в героя с ролью `tank`, если тот **не** в статусе `retreated`; если танк в `retreated` (или отсутствует в ростере) — общее правило по умолчанию. Это правило впервые фиксируется здесь: спека боссов описывала урок про порог отступления тематически, но не указывала, кто именно цель — без явного правила «отступление уводит от удара» механически не работало бы.

## `BattleTurn` / `BattleLog` / `BattleResult`

```json
// один BattleTurn
{
  "turn_number": 3,
  "events": [
    { "actor": "hero:mage-1", "action": { "type": "frost_bolt", "target": "boss" }, "amount": 18, "boss_hp_after": 640 },
    { "actor": "boss", "action": { "type": "single_target_hit", "target": "hero:tank-1" }, "amount": 12, "target_hp_after": 88 }
  ]
}
```

`BattleLog` — упорядоченный список `BattleTurn` за весь бой. `BattleResult` — `{ outcome: "victory"|"defeat"|"aborted", turns_taken: int, boss_id, hero_roster_snapshot }`.

## Условия завершения боя

- **Победа**: HP босса `<= 0`.
- **Поражение**: HP всех героев в ростере `<= 0`.
- **Аварийное завершение (`aborted`)**: превышен лимит ходов (`MaxTurns`, защитная константа — предлагается 30, не игровой баланс, а защита от зависания при некорректной комбинации контента). Логируется как ошибка конфигурации для последующего разбора, не показывается ребёнку как обычное поражение.

## Тестирование и валидация

- Property-тест на `frost_warden`: симуляция мага с «наивным» `TacticProgram` (`always -> frost_bolt`) и с «правильным» (`boss_phase_is(shielded) -> frost_bolt`, `always -> basic_attack`) при равных стартовых условиях — правильный побеждает не медленнее наивного (число ходов до победы). Это первая реализация property-теста, обещанного в спеке боссов.
- Тест на `stone_giant`: танк без правила retreat теряет HP быстрее в фазе `crumbling`, чем танк с правилом `self_resource_below(shield, 0.3) -> retreat`.
- Тест на лимит ходов: сконструированный тупиковый сценарий (например, целитель лечит быстрее, чем герои получают урон, а герои не могут пробить босса) корректно завершается `aborted`, а не бесконечным циклом.
- Тест на условия победы/поражения по HP.

## Открытые вопросы

- Все числа таблицы эффектов и `MaxTurns` — плейсхолдеры, требуют плейтеста.
- Правило таргетинга `stone_giant` (целится в `role:tank`) — решение этой спеки, не зафиксировано в бизнес-плане; при плейтесте может обнаружиться, что нужен более общий механизм «ролей передней линии», а не хардкод конкретной роли на конкретного босса.
